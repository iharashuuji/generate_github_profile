# Day 1：Git / GitHub 基礎 — PR駆動開発と Codespaces

## 1. この回で学ぶことと演習の意図

### この講座全体の理念

> **学んだ技術を、その場で自分のポートフォリオ（GitHub Profile）に反映して育てる。**

技術書を読んで終わりではなく、学んだその日に「自分の GitHub を訪れた人に見えるもの」が
変わっていく。この実感が、技術を定着させる一番の近道です。

### Day 1 の意図

**Codespaces 上で環境構築ゼロで開発を開始し、チーム開発のデファクトスタンダードである
「トピックブランチ作成 → PR → マージ」のフローを体得する。**

### なぜこれを学ぶのか（背景）

個人開発でも `main` ブランチへの直接 Push を避け、**PR（Pull Request）で差分を確認してから
マージする癖をつけること**が、安全な開発の第一歩となるためです。

実務では、次のような理由から PR が必須になります。

| 観点 | main 直 Push | PR 経由 |
|---|---|---|
| レビュー | 誰も差分を見ない | マージ前に他人（or 未来の自分）が差分を確認できる |
| 巻き戻し | 履歴から探すのが大変 | PR 単位でまとめて revert できる |
| CI | 壊れたコードが main に入る | マージ前にテスト・Lint を走らせられる |
| 記録 | commit しか残らない | 「なぜこの変更をしたか」の議論が残る |

「一人だから PR はいらない」ではなく、**一人のうちに手が覚えるまで練習しておく**のが
このDayのねらいです。

### 3回の全体像

| 回 | テーマ | この README に起きること |
|---|---|---|
| Day 1 | Git / GitHub 基礎 | 自分の手で自己紹介を書く（手動） |
| Day 2 | Linux & GitHub Actions | スクリプトが自動生成するようになる |
| Day 3 | Docker | 生成処理がコンテナの中で動くようになる |

## 2. 環境準備

### 2-1. このリポジトリを自分のアカウントにコピーする

このリポジトリは **Template Repository** です。`Fork` ではなく **`Use this template`** を使います。

1. 教材リポジトリのページで **`Use this template`** → **`Create a new repository`** をクリック
2. **Owner** … 必ず **自分の個人アカウント** を選択
3. **Repository name** … **自分の GitHub ユーザー名と完全に一致させる**
4. **Public** を選択（Private だと Profile README として表示されません）
5. `Create repository` をクリック

> ### ⚠️ 重要 1：リポジトリ名はユーザー名と完全一致させること
>
> GitHub には「**ユーザー名と同じ名前のリポジトリの README.md を、プロフィール画面に表示する**」
> という公式機能（Profile README）があります。
>
> ユーザー名が `octocat` なら、リポジトリ名も `octocat`。
> 大文字小文字の違いは問題ありませんが、**余計な文字を足すと機能しません**
> （`octocat-profile` や `my-octocat` では表示されません）。

> ### ⚠️ 重要 2：必ず「個人アカウント」配下に作成すること
>
> GitHub Codespaces の**無料枠（月 120 コア時間・15 GB ストレージ）は、
> 個人アカウントにのみ適用されます**。
>
> **組織（Organization）アカウント配下にコピーすると、初回の起動から課金対象になります。**
> Owner の欄が会社名やチーム名になっていないか、作成前に必ず確認してください。

### 2-2. Codespace を起動する

1. コピーして作られた**自分のリポジトリ**を開く
2. 緑色の **`Code`** ボタンをクリック
3. **`Codespaces`** タブを選択
4. **`Create codespace on main`** をクリック

ブラウザ上に VS Code の画面が立ち上がります。初回は 1〜2 分ほどかかります。
これで**あなたのローカル PC には何もインストールせずに**、開発環境が整いました。

画面下部の **ターミナル**（`Terminal` パネル）が、以降の作業場所です。
見当たらない場合は、メニューの `Terminal` → `New Terminal` で開けます。

## 3. 最低限必要なコマンドの早見表

今日の演習で使うコマンドは、この 3 つだけです。今は「これだけ分かれば進める」で十分です。

| コマンド | 読み方 | 何をするか |
|---|---|---|
| `pwd` | print working directory | **今どこにいるか**を表示する。迷子になったらまずこれ。 |
| `ls` | list | **今いる場所に何があるか**（ファイル・フォルダ）を一覧表示する。 |
| `cd <フォルダ名>` | change directory | **別のフォルダへ移動する**。`cd ..` で一つ上に戻る。 |

使用例：

```bash
pwd                 # → /workspaces/あなたのユーザー名  と表示される
ls                  # → README.md  docs  generate.sh ... と表示される
cd docs             # docs フォルダの中へ移動
ls                  # → DAY1.md  DAY2.md  DAY3.md
cd ..               # 一つ上（元の場所）に戻る
```

> **📘 詳しい解説は第二回で配布する『最低限の Linux コマンド』資料を参照してください。**
>
> 今日はこの 3 つだけ分かれば演習を完走できます。
> `cp` / `mv` / `rm` / `cat` / `mkdir` / `nano` といったコマンドは第二回でまとめて扱うので、
> **今の時点で覚えられなくても全く問題ありません。深追いは不要です。**

## 4. ステップ別手順

### Step 1：作業用のブランチを作る

まず、今どこにいるかを確認します。

```bash
pwd
```

`/workspaces/<あなたのユーザー名>` と表示されていれば OK です。

続いて、`main` から独立した**トピックブランチ**を作ります。

```bash
git switch -c feature/write-profile
```

`-c` は create（新規作成）の意味です。作成と同時にそのブランチへ移動します。
今いるブランチは、いつでもこれで確認できます。

```bash
git branch
```

`* feature/write-profile` のように `*` が付いているものが現在のブランチです。

> **なぜブランチを切るのか**
> `main` を「いつでも人に見せられる完成状態」に保ったまま、作業中の未完成なコードを
> 別の場所に隔離するためです。作業が失敗しても `main` は無傷で残ります。

### Step 2：README.md に自己紹介を書く

エディタ左側のファイル一覧から `README.md` をクリックして開き、
以下のコメントで囲まれた部分を、あなた自身の内容に書き換えてください。

```markdown
<!-- ここから自己紹介を書いてください -->

（この部分を書き換える）

<!-- ここまで自己紹介 -->
```

書く内容の例（すべて埋める必要はありません）：

- 名前・ハンドルネーム
- 今学んでいること、興味のある技術
- 好きな言語やツール
- 連絡先や外部リンク（X, Qiita, Zenn など）

Codespaces のエディタは**自動保存**されます（`Ctrl+S` / `Cmd+S` を押しても構いません）。

### Step 3：変更をコミットする

まず、何が変わったかを自分の目で確認します。

```bash
git status
```

`modified: README.md` と表示されるはずです。次に、変更の中身を見ます。

```bash
git diff
```

`-` で始まる赤い行が削除、`+` で始まる緑の行が追加です。
**コミットする前に diff を見る**——この習慣が、事故を防ぎます。

問題なければ、変更をステージングしてコミットします。

```bash
git add README.md
git commit -m "docs: 自己紹介を追加"
```

> **`git add` は何をしているのか**
> 「この変更をコミットに含める」と印を付ける作業です。
> 変更した全ファイルのうち、**どれを1つのコミットにまとめるか**を選べるようにするための仕組みで、
> これがあるおかげで「意味のある単位」でコミットを分けられます。

### Step 4：リモートへ Push する

```bash
git push -u origin feature/write-profile
```

`-u` は「このブランチの追跡先を origin に設定する」という意味で、初回だけ必要です。
2 回目以降は `git push` だけで済みます。

### Step 5：Pull Request を作成する

1. GitHub 上の自分のリポジトリをブラウザで開く
2. **`Compare & pull request`** という黄色いバナーが出ているのでクリック
   （出ていない場合は `Pull requests` タブ → `New pull request` → ブランチを選択）
3. base が `main`、compare が `feature/write-profile` になっていることを確認
4. タイトルと説明を書く（例：「自己紹介を追加」「Day1 の演習として README を更新」）
5. **`Create pull request`** をクリック

作成後、**`Files changed`** タブを必ず開いてください。
ここに表示されるのが「レビュアーが見る差分」です。**自分で自分の差分をレビューする**——
これが PR 駆動開発のいちばん大事な部分です。

### Step 6：マージする

差分に問題がなければ、

1. **`Merge pull request`** をクリック
2. **`Confirm merge`** をクリック
3. **`Delete branch`** をクリック（役目を終えたブランチは消してよい）

### Step 7：手元の main を最新にする

マージは GitHub 側（リモート）で行われたので、Codespace 内の `main` はまだ古いままです。

```bash
git switch main
git pull
```

これで手元の `main` にも自己紹介が反映されました。

### Step 8：プロフィール画面を確認する

ブラウザで `https://github.com/<あなたのユーザー名>` を開いてください。
**あなたが書いた自己紹介が、プロフィールページに表示されています。**

これが Profile README 機能です。今日の成果物は、もう世界中から見える状態になりました。

## 5. 確認ポイントとトラブルシューティング

### ✅ 確認ポイント

- [ ] リポジトリ名が自分の GitHub ユーザー名と完全に一致している
- [ ] リポジトリが **Public** になっている
- [ ] Owner が**個人アカウント**になっている（組織アカウントではない）
- [ ] `git log --oneline` に、自分のコミットとマージコミットが並んでいる
- [ ] `https://github.com/<ユーザー名>` に自己紹介が表示されている

### 🔧 よくあるトラブル

**Q. プロフィール画面に README が表示されない**

次の3点を確認してください。
1. リポジトリ名 = ユーザー名（完全一致）になっているか
2. リポジトリが Public か（Private では表示されません）
3. `README.md` がリポジトリの**一番上の階層**にあるか（`docs/` の中ではない）

**Q. `git push` で `Permission denied` と言われる**

自分のリポジトリではなく、教材の元リポジトリを直接 clone している可能性があります。
`git remote -v` を実行し、URL が自分のユーザー名になっているか確認してください。
違っていた場合は、`Use this template` からやり直すのが確実です。

**Q. `Compare & pull request` のバナーが出ない**

`Pull requests` タブ → `New pull request` から手動で作成できます。
base に `main`、compare に `feature/write-profile` を選んでください。

**Q. コミットしようとしたら `Please tell me who you are` と出る**

Git に名前とメールを教える必要があります。

```bash
git config --global user.name "あなたの名前"
git config --global user.email "あなたのGitHubメールアドレス"
```

**Q. ブランチを切り忘れて main で作業してしまった**

まだコミットしていなければ、そのまま `git switch -c feature/write-profile` を実行すれば
変更内容ごと新しいブランチへ移動できます。慌てなくて大丈夫です。

## 6. 技術的な深掘り解説

### このリポジトリの `git log` 自体が教材です

Codespace のターミナルで、次のコマンドを実行してみてください。

```bash
git log --oneline
```

この教材リポジトリが**どのように作られてきたか**が、一覧で表示されます。
注目してほしいのは、**「一度で完成させていない」**という点です。

```bash
git log --oneline | grep fix
```

`fix:` で始まるコミットがいくつか見つかります。これは**わざと残してある失敗の記録**です。
実際の開発では、一度書いたコードが間違っていて後から直す、ということが日常的に起こります。

その修正の中身は、次のコマンドで読めます。

```bash
git show <コミットハッシュ>
```

例えば `fix(ci):` のコミットを `git show` してみると、
「GitHub Actions が push に失敗したので権限設定を1行足した」という、
実際にありがちなトラブルとその解決がそのまま残っています。

> **なぜ失敗の記録を消さないのか**
> 「なぜこのコードがこうなっているのか」を後から知る唯一の手がかりだからです。
> 完璧な履歴より、**経緯が追える履歴**のほうが実務では価値があります。

### `git log` の便利な読み方

```bash
git log --oneline --graph        # ブランチの分岐・合流を図で表示
git log -p README.md             # README.md の変更履歴を差分付きで表示
git log --stat                   # 各コミットで何行変わったかを表示
git show HEAD                    # 直前のコミットの中身を表示
```

### なぜ「小さいコミット」が推奨されるのか

1 コミットに 10 個の変更を詰め込むと、そのうち 1 つだけ取り消したくなったときに
手作業で切り分けるしかありません。1 コミット 1 目的にしておけば、`git revert` で
その変更だけをきれいに巻き戻せます。

コミットは**セーブポイント**です。細かく置くほど、戻れる場所が増えます。

### Codespaces は「使い捨ての開発マシン」

Codespace の実体は、クラウド上に立ち上がる Linux コンテナです。
壊れても捨てて作り直せる——これが「環境構築でつまずかない」ことの正体です。

この「環境を使い捨てにできる」という考え方を、
**自分の手で作れるようにする**のが第三回の Docker 演習です。
