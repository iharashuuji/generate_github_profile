# Day 2：Linux & GitHub Actions 基礎 — 動的生成と自動化

## 1. この回で学ぶことと演習の意図

### この講座全体の理念

> **学んだ技術を、その場で自分のポートフォリオ（GitHub Profile）に反映して育てる。**

### Day 2 の意図

**手動更新から「プログラムによる動的生成（シェルスクリプト）」および
「クラウド上での自動コミット（CI/CD）」へステップアップする。**

第一回では、README.md を**あなたの手で**書きました。
今回は、その README.md を**スクリプトが自動で書く**ようにします。
さらにそのスクリプトを、**あなたの PC ではなくクラウド上（GitHub Actions）で動かします。**

### なぜこれを学ぶのか（背景）

Linux CLI の基本（`pwd` / `ls` / `cd` / `cp` / `rm` / `mv` / `cat` / `nano` / `mkdir`）を
学んだうえで、その先にある自動化の世界——**GitHub Actions（Bot）による代行**——に触れることで、
**運用の自動化（GitOps）の入口**を体験するためです。

実務では「手で毎回やっていた作業」を、次のように移していきます。

| 段階 | 誰がやるか | 今日どこを体験するか |
|---|---|---|
| 手作業 | 人間が毎回ファイルを編集 | ← 第一回でやったこと |
| スクリプト化 | 人間がコマンドを1回叩く | ← `generate.sh` を実行してみる |
| 自動化（CI/CD） | **Bot が勝手にやる** | ← **今日のゴール** |

「更新を忘れる」「更新の仕方を忘れる」「担当者が辞めて誰も更新できない」——
運用でよく起きるこれらの問題は、**自動化そのものをコードとしてリポジトリに置く**ことで解決します。
これが GitOps の考え方です。

### 今日のゴール

> `main` に push した瞬間、**GitHub 上の Bot** が `generate.sh` を実行し、
> README.md を自動で書き換えてコミットしてくれる。
> その結果が **Profile 画面**と **GitHub Pages** の両方に反映される。

### ⚠️ スコープについて（重要）

**`generate.sh` の中身（`sed` / `date` / `curl`）は配布済みコードとして提示するのみです。
受講者のみなさんが書いたり、改造したりする必要はありません。**

> **このコードは配布済みです。中身を全部理解できなくても心配ありません。
> 今日のゴールは、このコードが Actions 上で実行され、
> Profile と Pages の両方が自動で更新される様子を体験することです。**

コードの解説は講義で行います。手を動かすのは「実行して、結果を見る」ところに集中してください。

## 2. 環境準備

### 2-1. Codespace を起動する

第一回と同じ手順です。

1. 自分のリポジトリ（リポジトリ名 = 自分のユーザー名）を開く
2. **`Code`** ボタン → **`Codespaces`** タブ → **`Create codespace on main`**

> ### ⚠️ 無料枠のリマインド
>
> Codespaces の無料枠（月 120 コア時間・15 GB ストレージ）は
> **個人アカウントにのみ適用されます。** 組織アカウント配下のリポジトリでは課金対象です。
> Owner が自分の個人アカウントになっていることを確認してください。
>
> また、**使い終わったら必ず Codespace を削除**してください（手順は末尾の第7章）。

### 2-2. 最新の main を取り込む

前回の作業から時間が空いている場合、念のため最新化しておきます。

```bash
git switch main
git pull
```

### 2-3. 今日使う Linux コマンド

第一回では `pwd` / `ls` / `cd` の3つだけを使いました。今日はこれに数個加わります。

| コマンド | 何をするか |
|---|---|
| `pwd` | 今どこにいるかを表示 |
| `ls` | 今いる場所のファイル一覧（`ls -l` で詳細表示） |
| `cd` | フォルダを移動（`cd ..` で一つ上へ） |
| `cat <ファイル>` | ファイルの中身を表示する |
| `cp <元> <先>` | ファイルをコピーする |
| `mv <元> <先>` | ファイルを移動する / 名前を変える |
| `rm <ファイル>` | ファイルを削除する（**取り消せません**） |
| `mkdir <名前>` | フォルダを作る |
| `nano <ファイル>` | ターミナル内でファイルを編集する（`Ctrl+O` 保存 → `Ctrl+X` 終了） |

## 3. ステップ別手順

### Step 1：配布済みスクリプトを読んでみる

まず、今日の主役を眺めます。

```bash
cat generate.sh
```

`sed`、`date`、`curl` といったコマンドが並んでいます。

> **繰り返しになりますが、このコードは配布済みです。
> 中身を全部理解できなくても心配ありません。**
> 今日のゴールは、このコードが Actions 上で実行され、
> Profile と Pages の両方が自動で更新される様子を体験することです。

ざっくり言うと、このスクリプトは次の3つをしています。

1. `date` で**現在時刻**を取る
2. `curl` で **GitHub API** から公開リポジトリ数を取る
3. `sed` で `template.md` の `{{...}}` を**実際の値に置き換えて** `README.md` に書き出す

型紙のほうも見てみましょう。

```bash
cat template.md
```

`{{USER_NAME}}` や `{{BUILD_DATE}}` という**プレースホルダ（穴）**が空いています。
ここに値が流し込まれます。

### Step 2：手元で1回だけ実行してみる

Actions に任せる前に、Codespace の中で動かして結果を確かめます。

```bash
./generate.sh
```

`✅ README.md を生成しました` と表示されれば成功です。
何が変わったかを見てみましょう。

```bash
git diff
```

あなたが第一回で書いた自己紹介が、**生成された内容に置き換わっている**はずです。

> **⚠️ ここで書き換わった README.md は、いったん元に戻します。**
> 自動化の効果を Actions 側で確認したいので、手元の変更は破棄しておきます。
>
> ```bash
> git restore README.md
> ```
>
> `git restore` は「まだコミットしていない変更を捨てて、元に戻す」コマンドです。

### Step 3：ワークフローを確認する

自動化の設定ファイルを見てみます。

```bash
cat .github/workflows/update-profile.yml
```

このファイルが「**いつ・どこで・何をするか**」の指示書です。

| 項目 | 意味 |
|---|---|
| `on: push: branches: [main]` | main に push されたら動く |
| `on: workflow_dispatch` | 画面のボタンから手動でも動かせる |
| `permissions: contents: write` | Bot がリポジトリに書き込む権限 |
| `runs-on: ubuntu-latest` | GitHub が貸してくれる Ubuntu マシンで動かす |
| `actions/checkout@v5` | まずリポジトリのコードを取ってくる |
| `run: ./generate.sh` | **生成スクリプトを実行する（← 第三回で差し替える箇所）** |
| 最後のブロック | 生成結果を Bot 名義でコミットして push する |

> **`|| echo "no changes"` は何のため？**
> 生成結果が前回と全く同じだと、`git commit` は「コミットするものが無い」として
> **エラー終了**します。すると workflow 全体が失敗扱いになってしまう。
> 「変更が無い場合はメッセージを出すだけで正常終了する」ようにするための保険です。

### Step 4：GitHub Pages を有効にする（1回だけの手動設定）

生成された README.md を、Web サイトとしても公開します。

1. 自分のリポジトリの **`Settings`** タブを開く
2. 左メニューの **`Pages`** をクリック
3. **Source** を **`Deploy from a branch`** に設定
4. **Branch** を **`main`** / **`/ (root)`** に設定
5. **`Save`** をクリック

数分後、`https://<あなたのユーザー名>.github.io/<リポジトリ名>/` で公開されます
（リポジトリ名 = ユーザー名なので、`https://<ユーザー名>.github.io/<ユーザー名>/` になります）。

> **この設定は最初の1回だけです。**
> 一度有効にしておけば、以降は README.md が更新されるたびに Pages も自動で追従します。
> つまり、**ワークフローが README.md を書き換えて push した瞬間、
> Profile 画面と Pages サイトの両方が自動更新される**状態になります。

### Step 5：ワークフローを手動実行する

いよいよ Bot に働いてもらいます。

1. リポジトリの **`Actions`** タブを開く
2. 左メニューから **`Update Profile`** を選択
3. 右側の **`Run workflow`** ボタンをクリック
4. ブランチが `main` になっていることを確認して、緑の **`Run workflow`** をクリック

数十秒待つと、一覧に実行結果が現れます。行をクリックすると、
**各ステップのログ**をリアルタイムで読めます。

`プロフィールを再生成` ステップを開くと、
`✅ README.md を生成しました` という、さきほど手元で見たのと同じ出力があるはずです。
**同じスクリプトが、今度はクラウド上のマシンで動いている**わけです。

### Step 6：結果を確認する

3か所を確認してください。

1. **コミット履歴** … リポジトリのトップで `commits` をクリック。
   `github-actions[bot]` による `chore: update profile` というコミットがあります。
   **あなたが書いていないコミットが積まれている**——これが自動化の実体です。
2. **プロフィール画面** … `https://github.com/<ユーザー名>` に、
   生成された内容（更新日時・公開リポジトリ数）が表示されています。
3. **Pages サイト** … `https://<ユーザー名>.github.io/<ユーザー名>/` にも同じ内容が出ています。

### Step 7：手元にも取り込む

Bot がリモート側でコミットしたので、Codespace の中身はまだ古いままです。

```bash
git pull
git log --oneline | head -5
```

`github-actions[bot]` のコミットが取り込まれました。
