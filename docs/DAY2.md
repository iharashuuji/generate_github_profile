# Day 2：Linux & GitHub Actions 基礎 — 動的生成と自動化

## 1. この回で学ぶことと演習の意図

### この講座全体の理念

> **学んだ技術を、その場で自分のポートフォリオ（GitHub Profile）に反映して育てる。**

### Day 2 の意図

**手動更新から「プログラムによる動的生成（シェルスクリプト）」および
「クラウド上での自動コミット（CI/CD）」へステップアップする。**

第一回では、README.md を**あなたの手で**書きました。
今回は、その README.md を**スクリプトが自動で書く**ようにします。
さらにそのスクリプトを、**あなたの PC ではなくクラウド上（GitHub Actions）で動かします。**

### なぜこれを学ぶのか（背景）

Linux CLI の基本（`pwd` / `ls` / `cd` / `cp` / `rm` / `mv` / `cat` / `nano` / `mkdir`）を
学んだうえで、その先にある自動化の世界——**GitHub Actions（Bot）による代行**——に触れることで、
**運用の自動化（GitOps）の入口**を体験するためです。

実務では「手で毎回やっていた作業」を、次のように移していきます。

| 段階 | 誰がやるか | 今日どこを体験するか |
|---|---|---|
| 手作業 | 人間が毎回ファイルを編集 | ← 第一回でやったこと |
| スクリプト化 | 人間がコマンドを1回叩く | ← `generate.sh` を実行してみる |
| 自動化（CI/CD） | **Bot が勝手にやる** | ← **今日のゴール** |

「更新を忘れる」「更新の仕方を忘れる」「担当者が辞めて誰も更新できない」——
運用でよく起きるこれらの問題は、**自動化そのものをコードとしてリポジトリに置く**ことで解決します。
これが GitOps の考え方です。

### 今日のゴール

> `main` に push した瞬間、**GitHub 上の Bot** が `generate.sh` を実行し、
> README.md を自動で書き換えてコミットしてくれる。
> その結果が **Profile 画面**と **GitHub Pages** の両方に反映される。

### ⚠️ スコープについて（重要）

**`generate.sh` の中身（`sed` / `date` / `curl`）は配布済みコードとして提示するのみです。
受講者のみなさんが書いたり、改造したりする必要はありません。**

> **このコードは配布済みです。中身を全部理解できなくても心配ありません。
> 今日のゴールは、このコードが Actions 上で実行され、
> Profile と Pages の両方が自動で更新される様子を体験することです。**

コードの解説は講義で行います。手を動かすのは「実行して、結果を見る」ところに集中してください。

## 2. 環境準備

### 2-1. Codespace を起動する

第一回と同じ手順です。

1. 自分のリポジトリ（リポジトリ名 = 自分のユーザー名）を開く
2. **`Code`** ボタン → **`Codespaces`** タブ → **`Create codespace on main`**

> ### ⚠️ 無料枠のリマインド
>
> Codespaces の無料枠（月 120 コア時間・15 GB ストレージ）は
> **個人アカウントにのみ適用されます。** 組織アカウント配下のリポジトリでは課金対象です。
> Owner が自分の個人アカウントになっていることを確認してください。
>
> また、**使い終わったら必ず Codespace を削除**してください（手順は末尾の第7章）。

### 2-2. 最新の main を取り込む

前回の作業から時間が空いている場合、念のため最新化しておきます。

```bash
git switch main
git pull
```

### 2-3. 今日使う Linux コマンド

第一回では `pwd` / `ls` / `cd` の3つだけを使いました。今日はこれに数個加わります。

| コマンド | 何をするか |
|---|---|
| `pwd` | 今どこにいるかを表示 |
| `ls` | 今いる場所のファイル一覧（`ls -l` で詳細表示） |
| `cd` | フォルダを移動（`cd ..` で一つ上へ） |
| `cat <ファイル>` | ファイルの中身を表示する |
| `cp <元> <先>` | ファイルをコピーする |
| `mv <元> <先>` | ファイルを移動する / 名前を変える |
| `rm <ファイル>` | ファイルを削除する（**取り消せません**） |
| `mkdir <名前>` | フォルダを作る |
| `nano <ファイル>` | ターミナル内でファイルを編集する（`Ctrl+O` 保存 → `Ctrl+X` 終了） |

## 3. ステップ別手順

### Step 1：配布済みスクリプトを読んでみる

まず、今日の主役を眺めます。

```bash
cat generate.sh
```

`sed`、`date`、`curl` といったコマンドが並んでいます。

> **繰り返しになりますが、このコードは配布済みです。
> 中身を全部理解できなくても心配ありません。**
> 今日のゴールは、このコードが Actions 上で実行され、
> Profile と Pages の両方が自動で更新される様子を体験することです。

ざっくり言うと、このスクリプトは次の3つをしています。

1. `date` で**現在時刻**を取る
2. `curl` で **GitHub API** から公開リポジトリ数を取る
3. `sed` で `template.md` の `{{...}}` を**実際の値に置き換えて** `README.md` に書き出す

型紙のほうも見てみましょう。

```bash
cat template.md
```

`{{USER_NAME}}` や `{{BUILD_DATE}}` という**プレースホルダ（穴）**が空いています。
ここに値が流し込まれます。

### Step 2：手元で1回だけ実行してみる

Actions に任せる前に、Codespace の中で動かして結果を確かめます。

```bash
./generate.sh
```

`✅ README.md を生成しました` と表示されれば成功です。
何が変わったかを見てみましょう。

```bash
git diff
```

あなたが第一回で書いた自己紹介が、**生成された内容に置き換わっている**はずです。

> **⚠️ ここで書き換わった README.md は、いったん元に戻します。**
> 自動化の効果を Actions 側で確認したいので、手元の変更は破棄しておきます。
>
> ```bash
> git restore README.md
> ```
>
> `git restore` は「まだコミットしていない変更を捨てて、元に戻す」コマンドです。

### Step 3：ワークフローを確認する

自動化の設定ファイルを見てみます。

```bash
cat .github/workflows/update-profile.yml
```

このファイルが「**いつ・どこで・何をするか**」の指示書です。

| 項目 | 意味 |
|---|---|
| `on: push: branches: [main]` | main に push されたら動く |
| `on: workflow_dispatch` | 画面のボタンから手動でも動かせる |
| `permissions: contents: write` | Bot がリポジトリに書き込む権限 |
| `runs-on: ubuntu-latest` | GitHub が貸してくれる Ubuntu マシンで動かす |
| `actions/checkout@v5` | まずリポジトリのコードを取ってくる |
| `run: ./generate.sh` | **生成スクリプトを実行する（← 第三回で差し替える箇所）** |
| 最後のブロック | 生成結果を Bot 名義でコミットして push する |

> **`|| echo "no changes"` は何のため？**
> 生成結果が前回と全く同じだと、`git commit` は「コミットするものが無い」として
> **エラー終了**します。すると workflow 全体が失敗扱いになってしまう。
> 「変更が無い場合はメッセージを出すだけで正常終了する」ようにするための保険です。

### Step 4：GitHub Pages を有効にする（1回だけの手動設定）

生成された README.md を、Web サイトとしても公開します。

1. 自分のリポジトリの **`Settings`** タブを開く
2. 左メニューの **`Pages`** をクリック
3. **Source** を **`Deploy from a branch`** に設定
4. **Branch** を **`main`** / **`/ (root)`** に設定
5. **`Save`** をクリック

数分後、`https://<あなたのユーザー名>.github.io/<リポジトリ名>/` で公開されます
（リポジトリ名 = ユーザー名なので、`https://<ユーザー名>.github.io/<ユーザー名>/` になります）。

> **この設定は最初の1回だけです。**
> 一度有効にしておけば、以降は README.md が更新されるたびに Pages も自動で追従します。
> つまり、**ワークフローが README.md を書き換えて push した瞬間、
> Profile 画面と Pages サイトの両方が自動更新される**状態になります。

### Step 5：ワークフローを手動実行する

いよいよ Bot に働いてもらいます。

1. リポジトリの **`Actions`** タブを開く
2. 左メニューから **`Update Profile`** を選択
3. 右側の **`Run workflow`** ボタンをクリック
4. ブランチが `main` になっていることを確認して、緑の **`Run workflow`** をクリック

数十秒待つと、一覧に実行結果が現れます。行をクリックすると、
**各ステップのログ**をリアルタイムで読めます。

`プロフィールを再生成` ステップを開くと、
`✅ README.md を生成しました` という、さきほど手元で見たのと同じ出力があるはずです。
**同じスクリプトが、今度はクラウド上のマシンで動いている**わけです。

### Step 6：結果を確認する

3か所を確認してください。

1. **コミット履歴** … リポジトリのトップで `commits` をクリック。
   `github-actions[bot]` による `chore: update profile` というコミットがあります。
   **あなたが書いていないコミットが積まれている**——これが自動化の実体です。
2. **プロフィール画面** … `https://github.com/<ユーザー名>` に、
   生成された内容（更新日時・公開リポジトリ数）が表示されています。
3. **Pages サイト** … `https://<ユーザー名>.github.io/<ユーザー名>/` にも同じ内容が出ています。

### Step 7：手元にも取り込む

Bot がリモート側でコミットしたので、Codespace の中身はまだ古いままです。

```bash
git pull
git log --oneline | head -5
```

`github-actions[bot]` のコミットが取り込まれました。

## 4. 確認ポイントとトラブルシューティング

### ✅ 確認ポイント

- [ ] `Actions` タブの実行結果が**緑のチェック**になっている
- [ ] `github-actions[bot]` 名義のコミットが履歴に積まれている
- [ ] プロフィール画面に、生成された更新日時が表示されている
- [ ] Pages サイトが表示される（Settings → Pages に緑のリンクが出ている）

### 🔧 よくあるトラブル

**Q. `Permission to ... denied to github-actions[bot]` / `403` でワークフローが失敗する**

`update-profile.yml` の `permissions: contents: write` が抜けています。
Bot がリポジトリへ書き込むための権限指定です。

なお、このリポジトリの履歴には**この失敗と修正が実際に記録されています。**

```bash
git log --oneline | grep "fix(ci)"
git show <表示されたハッシュ>
```

`+permissions:` の 2 行が足された差分が見えます。**実際にありがちな詰まり方**なので、
エラーメッセージと修正内容をセットで覚えておくと役に立ちます。

**Q. `./generate.sh: Permission denied` と言われる**

スクリプトに実行権限がありません。次のコマンドで付与できます。

```bash
chmod +x generate.sh
```

（このリポジトリでは最初から付与済みですが、自分で新しくスクリプトを作った時には必要になります。）

**Q. `Actions` タブに `Update Profile` が出てこない**

`.github/workflows/update-profile.yml` が `main` ブランチに存在するか確認してください。
ワークフローはデフォルトブランチに置かれていないと認識されないことがあります。

**Q. 公開リポジトリ数が `N/A` になる**

GitHub API の呼び出しに失敗しています。認証なし API の制限（1時間60リクエスト）に
達した可能性がありますが、**演習の成否には影響しません。**
時間をおいて再実行すれば通常の値に戻ります。

**Q. Pages サイトが 404 になる**

- Settings → Pages の設定直後は、反映まで数分かかります
- Source が `Deploy from a branch`、Branch が `main` / `/ (root)` になっているか確認
- リポジトリが Public になっているか確認

**Q. 生成結果を元に戻したい（自己紹介を書き直したい）**

`template.md` を編集してから、再度ワークフローを実行してください。
`README.md` は毎回生成し直されるため、**直接編集しても次回の実行で上書きされます。**
今後は「`template.md` が原本、`README.md` は生成物」という関係になります。

## 5. 技術的な深掘り解説

### なぜ「生成物」と「原本」を分けるのか

今日を境に、`README.md` の立場が変わりました。

| ファイル | 立場 | 編集してよいか |
|---|---|---|
| `template.md` | **原本（ソース）** | ✅ ここを編集する |
| `README.md` | **生成物（ビルド結果）** | ❌ 編集しても上書きされる |

ソフトウェア開発では、この「**ソースと成果物を分ける**」考え方が至るところに現れます
（`.c` → 実行ファイル、`.ts` → `.js`、Markdown → HTML）。
**人が触る場所を1か所に固定する**ことで、変更の入り口が明確になり、事故が減ります。

### `set -eu` は何を守っているか

`generate.sh` の冒頭にある 1 行です。

- `set -e` … コマンドが 1 つでも失敗したら、**その場で停止**する
  （途中でエラーが出たのに最後まで走り抜けて、壊れたファイルを出力する事故を防ぐ）
- `set -u` … **未定義の変数**を使おうとしたらエラーにする
  （タイポで空文字が入り、意図せず空の README ができる事故を防ぐ）

自動化されたスクリプトは**誰も見ていない場所で動きます。**
だからこそ「失敗したら黙って進まず、はっきり止まる」ことが重要です。

### sed の区切り文字にまつわる実話

`generate.sh` の `sed` は `s|...|...|g` と、`|` を区切り文字に使っています。
教科書でよく見る `s/.../.../g` ではありません。

理由は、置換する値に `/` が含まれると sed が混乱するからです。
このリポジトリの履歴には、その修正が残っています。

```bash
git log --oneline | grep "fix(generate.sh)"
git show <表示されたハッシュ>
```

**最初は `/` で書いていて、`BUILD_HOST` に `Linux / codespaces-xxx` という
スラッシュ入りの値が入った瞬間に壊れた**——という、ごく普通の失敗の記録です。

### GitHub Actions の課金と無料枠

- **Public リポジトリでの Actions 実行は無料**です（今回の演習は該当）
- Private リポジトリの場合は無料枠（月 2,000 分）を消費します

Codespaces の枠とは**別勘定**である点に注意してください。

### この先にあるもの

今日作った自動化には、まだ弱点があります。

> `runs-on: ubuntu-latest` のマシンに入っているコマンドの**バージョンが変わったら、
> 生成結果も変わってしまうかもしれない。**

「自分の Codespace では動いたのに、Actions では動かない」——
この**環境差分**の問題を解決するのが、第三回の Docker です。

## 6. 後片付け：Codespace の削除方法

> ### ⚠️ 「停止」と「削除」は別物です
>
> Codespace を**停止（Stop）しただけでは、ストレージ枠を消費し続けます。**
> 無料枠は月 15 GB ストレージ。使い終わったら**削除（Delete）**まで行ってください。
>
> | 操作 | コア時間（実行時間） | ストレージ |
> |---|---|---|
> | 停止（Stop） | 止まる ✅ | **消費し続ける ❌** |
> | 削除（Delete） | 止まる ✅ | 解放される ✅ |

### 削除の手順

1. ブラウザで **<https://github.com/codespaces>** を開く
2. 一覧から、今日使った Codespace を見つける
3. 右端の **`...`**（三点メニュー）をクリック
4. **`Delete`** をクリック
5. 確認ダイアログで **`Delete`** を再度クリック

### 削除しても大丈夫？

**はい。`git push` 済みの変更は GitHub 上に保存されているため、消えません。**
次回また `Code` → `Codespaces` → `Create codespace on main` で、
最新の状態から新しい環境を立ち上げられます。

> **⚠️ push していない変更は消えます。**
> 削除の前に、必ず次を実行して未 push の変更が無いか確認してください。
>
> ```bash
> git status
> ```
>
> `nothing to commit, working tree clean` かつ
> `Your branch is up to date with 'origin/main'` と表示されていれば、安全に削除できます。
